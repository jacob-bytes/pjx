## A. 三个真 bug —— 都是第二轮我自己引入的

这三条不是美化，是**做错了**，建议无条件先修。

### A1 详情页「实时」档的图表是冻结的 🔴

**实测确认。** 现象：详情页顶部数字每秒在跳，下面 7 张图一动不动。

根因在两处叠加：

```ts
// public/mock.ts:245
? direct.slice(-points)        // ← slice 复制出新数组
// ...
historyCache.set(key, series)  // ← 然后把这个副本永久缓存
```

```tsx
// node-detail.tsx:82
const series = useMemo(() => {...}, [node, range])
// node 是同一个对象（mock 原地改数据），range 不变 → 这个 memo 永远不重算
```

`slice()` 产生的是**首帧那一刻的快照**，之后被缓存、被 memo 锁死。

**实测证据**：虚拟时间跑 120 秒（约 120 次 tick），同一节点跑 4 轮：

| 轮次 | 头部（实时值） | 图上最后一点 | 差 |
| --- | --- | --- | --- |
| 1 | 40.6% | 37.8% | 2.8pp |
| 2 | 41.9% | 39.2% | 2.7pp |
| 3 | 44.2% | 39.4% | 4.8pp |
| 4 | 41.4% | 37.6% | 3.8pp |

图上值被钉在 37.6~39.4，而种子基准是 41.6 —— 正好等于 `41.6 + sin(4.917)×4 ≈ 37.7`，
也就是**种子序列最后一个点的确定性取值**，不是随机巧合。头部则围绕基准随机游走。

**影响**：内存与 Swap、磁盘、延迟趋势等全部图表在实时档都不更新。
讽刺的是，页面现在"很流畅"正是因为它坏了 —— 修好之后每秒真的有 7 张图要重画。

### A2 切到历史档，时间轴标签差 60 倍 🔴

**实测确认。** `RANGES` 只定义了 `points`，详情页却把它当秒数用：

```tsx
const windowSeconds = RANGES.find((item) => item.key === range)?.points ?? 60
```

| 档位 | points | 真实跨度 | 现在渲染成 |
| --- | --- | --- | --- |
| 实时 | 60 | 1 分钟 | 1 分钟 ✓ |
| 4 小时 | 120 | 4 小时 | **2 分钟** ✗ |
| 1 天 | 144 | 24 小时 | **2.4 分钟** ✗ |
| 7 天 | 168 | 168 小时 | **2.8 分钟** ✗ |

横轴、页脚「N 个采样点 · 1s 实时」、底部「N 窗口」三处全错。
实时档碰巧对（1Hz 下点数=秒数），所以只在切档后才暴露。

### A3 6 条 ping 线几乎同色，根本分不开 🟠

**实测确认。** 我上一轮为了"克制"用 `color-mix(chart-1 → chart-3)` 做 6 档色阶，
但这两个 token 的明度几乎一样（0.62 vs 0.60），混出来是 6 个近乎相同的青蓝色：

| 档 | hex（浅色） | 与相邻档的亮度差 |
| --- | --- | --- |
| 1 | `#0099a0` | — |
| 2 | `#1095a5` | 1.00% |
| 3 | `#2091aa` | 0.86% |
| 4 | `#2f8cb0` | 0.97% |
| 5 | `#3f88b5` | 0.49% |
| 6 | `#4f84ba` | 0.29% |

相邻两档亮度差不到 1%，远低于可分辨阈值。**当时那句"同源色阶更克制"是想当然，没验算。**

## B. 无障碍与可用性（`ui-ux-pro-max` 有明确依据）

### B1 图表只能鼠标悬停，触屏完全没法看数值 🟠

skill 的 UX 条目：**Hover vs Tap — "Hover effects don't work on touch devices"，
严重度 High**。

`TimeSeriesChart` 只有 `onMouseMove` / `onMouseLeave`。前台是移动优先的页面，
手机上 7 张图都没有任何读数手段 —— 只能看形状。

修法：改用 Pointer Events，触摸时锁定最近点并显示提示（点空白取消）。

### B2 多序列只靠颜色区分 🟠

skill 的 chart 条目明确写：
**"Differentiate series by line style (solid/dashed/dotted) not color alone.
Add pattern overlays for colorblind users."** 无障碍等级 AA 的必备项。

现状：6 条 ping 线全是实线、只有颜色差别 —— 而按 A3，颜色还几乎一样。
另外 skill 也提示 **"more than 6 series = visual noise"**，我们正好卡在 6 条上限。

修法：颜色 + 线型双通道（实线 / 长虚线 / 短虚线 …），图例同时显示线型。

### B3 虚线参考线没有图例，但 tooltip 里有 🟡

「内存与 Swap」图有两条虚线（内存总量、Swap 总量）。图例把它们过滤掉了
（`series.filter(item => !item.reference)`），但 tooltip 又会显示它们。
结果：不悬停就不知道那两条虚线是什么。p1 的图例是有「RAM 总量 / Swap 总量」的。

### B4 动效时长体系是空的 🟡

规范 §7 写"三档时长 120/180/240ms + 单条缓动"，`globals.css` 也定义了
`--dur-1/2/3` 和 `--ease` —— 但**全项目引用数都是 0**。实际用的是：

| 时长 | 处数 | 评价 |
| --- | --- | --- |
| `duration-100` | 17 | 低于 skill 建议的 150ms 下限 |
| `duration-150/200` | 5 | 合理 |
| `duration-300` | 2 | 合理 |
| `duration-500` | 1 | Sheet 滑入，偏慢 |
| `duration-700` | 2 | KPI / 指标卡进度条，**远超 500ms 上限** |

`--ease` 从未生效，所有过渡都在用 Tailwind 默认缓动。
规范 §7 还写了 `--shadow-pop`，这个 token **根本不存在**。

## D. 我建议**不要**做的

- **给卡片加阴影。** p4 确实有，但你的规范是"只有浮层有阴影"。上一轮用"压暗背景 + 描边"达到同样分层，加阴影会让整套 UI 松动。
- **引入图表库（uPlot / Recharts）。** skill 的 chart 条目在 ≥1000 点时才建议上 Canvas；我们最多 168 点 / 7 张图，SVG 足够，引库要 +30~80KB gzip，还会打破现在的 token 联动。
- **炫技动效（stagger 入场、滚动动画、GSAP）。** skill 在 density=8 的仪表盘场景下推荐的是 "Stagger List"，但这与规范 §6「禁止逐卡入场动画」直接冲突 —— 以规范为准。
- **换字体。** skill 推 Fira Code / Fira Sans，但 IBM Plex Sans + JetBrains Mono 已经落地且自托管，换字体是纯损失。

## F. 实施记录（11 项全部完成）

### A1 实时档图表冻结 ✅

两处根因一起改：

1. `historyFor` / `pingHistoryFor` 的实时分支改为**直接返回 live 数组引用**，不 `slice` 复制、不进缓存

   被 memo 锁死后不像 live 数组那样会原地更新，这才是图表停在打开瞬间的直接原因

**复测（120 秒虚拟时间，同节点 2 轮）**：

| | 修复前 | 修复后 |
| --- | --- | --- |
| 头部 vs 图上差值 | 2.7 ~ 4.8pp（4 轮一致偏下） | **0.0pp / 0.0pp** |

顺带把 ping 历史长度从 40 对齐到 60，与实时窗口一致。

## G. 第三轮补充：对齐 ink 主题的配色

对照上游主题 [komari-theme-ink](https://github.com/jacob-bytes/komari-theme-ink) 的
README 设计 token 表后，发现我在 A3 里的处理**方向错了**，已回改。

### 我错在哪

ink 的核心原则写得很明确：

> **3 语义色收敛** —— 蓝（primary）· 绿（success）· 红（danger），**无紫橙青绿噪音**
> `--primary` 用途：图表主线 / 选中态 / hover 边框 / sparkline

而 ink 的 `docs/DetailPageRework.md` 里还有一条：

> 颜色统一为中性 + **单一强调色**

也就是说 ink **全站只用一个蓝色画所有图表线**，靠别的手段区分序列。
我在 A3 里给 6 条 ping 线配了 6 个色相还新增 `--chart-6` 紫罗兰 —— 正好反了。

我最初"同源色阶"的**方向是对的**，错在实现：拿 `chart-1`(L0.62) 和 `chart-3`(L0.60)
混色，两者明度只差 0.02，所以 6 档看起来是同一个颜色。

### 改了什么

| 项 | 改前 | 改后 |
| --- | --- | --- |
| `--brand` / `--ring` | `oklch(0.521 0.1 200)` 青 | **`oklch(0.53 0.16 258)` 深蓝**（ink 的 primary） |
| 深色中性色 | hue 255，彩度 0.006（近中性灰） | **hue 265，彩度 0.018**（蓝紫倾向） |
| `--chart-1` | 青 | **跟随品牌蓝**（ink：primary 就是图表主线） |
| `--chart-3` | `oklch(0.6 0.1 250)` 蓝 | **`oklch(0.6 0.02 258)` 中性灰蓝** |
| `--chart-6` | 紫罗兰（我上一轮加的） | **删除** |
| ping 6 条线 | 6 个色相 | **`--ping-1..6` 单一蓝 6 档明度 + 线型** |

关于 `--brand` 明度：ink 原值是 `0.55`，直接抄过来在 `--muted` 上只有 **4.32:1**，
过不了我们自己的 4.5 门槛（`npm run check:contrast`）。压到 `0.53` 后
background/card/muted 分别是 4.95 / 5.37 / 4.71，色相与彩度和 ink 一致。

`--chart-3` 为什么要改成中性：它和 `--chart-1` 在「CPU 与负载」双轴图里成对出现，
两个都是蓝且明度接近的话，会原样重演"6 条线分不开"那个坑。

### 阶梯的实测数据

| 方案 | 两两最小色距 | 最浅/最暗档可见度 |
| --- | --- | --- |
| 最初 chart-1→chart-3 色阶（坏） | 0.0335 | — |
| 上一轮 6 个色相 | 0.1713 | — |
| **现在 单一蓝 6 档（浅色）** | **0.1130** | 3.21:1 ✓ |
| **现在 单一蓝 6 档（深色）** | **0.1448** | 3.18:1 ✓ |

**诚实地讲：单色阶梯的可分性（0.113）低于多色相（0.171）。** 这是"单一强调色"的固有代价。
所以线型不是可选项而是必需品 —— 6 条线按 `实线 / 长虚线 / 点线` 分三组，
颜色 × 线型两个通道乘起来才够用。这也正好满足图表无障碍的硬要求（不能只靠颜色）。

### 验证

- `tsc -b` / `npm run build` / `npm run check:contrast` 全绿（两套主题 8 个文字 token 全部 ≥4.5:1）
- 渲染了 token 色板截图肉眼确认：浅色 brand 已是深蓝、ping 1..6 是一条连续蓝色阶梯、
  深色底有蓝紫倾向
- 详情页 6 条 ping 线确认使用 `--ping-1..6`，线型出现 `6 3`（长虚线）与 `2 3`（点线）
- 列表页 / 详情页 / 后台 Sheet 全部正常渲染

### 仍未对齐 ink 的一处（需你决定）

`--chart-4` 绿（入站）与 `--chart-5` 红（出站）现在成了调色板里唯一的"噪音"——
而且 ink 规定绿**只用于在线状态**、红**只用于异常/丢包**，我们却拿它们画流量方向。
配色收敛之后这两个颜色比之前更显眼了（见色板截图）。
改法是把入站/出站换成蓝 + 中性灰，磁盘的琥珀保留为唯一副色。**这条没动，等你定。**
