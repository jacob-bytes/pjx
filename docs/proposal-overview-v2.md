# 总览页 v2 方案（评审稿）

> 渲染稿：`proposal-overview-v2.html`（右下角可切深浅色）、`proposal-v2-light.png`、`proposal-v2-dark.png`
> 本文只描述方案，**尚未改任何产品代码**。

## 一、为什么现在"看不出来好看"（诊断）

先说清楚病因，否则改动就是碰运气。当前总览页的问题不是"丑"，是**平**：

| 症状 | 实测 |
| --- | --- |
| 顶部 5 张卡片**完全等价** | 同宽、同高（83px）、同一套"图标 + 大数字 + 一行说明"，只有 3px 色条区分异常 |
| 表格**只有"当下"没有"历史"** | 8 列全是瞬时值（IP / agent / 最后上报 / 关注），一行 1000px 里没有任何时间维度 |
| 表格**横向太空** | 内容自然宽度 714px，容器 1024px —— 310px 是空着的（§AW 实测） |
| 页面**只描述、不行动** | 要看"现在该处理什么"必须自己扫 12 行找徽章；没有把异常提到眼前的入口 |
| 行高偏松 | 50px；同屏只能看 12 行 |

一句话：**信息密度和视觉重心都没有分层** —— 5 张一样的卡 + 一张平铺的表，所以怎么修 craft 都"看不出来"。

## 二、方案：把"一样的卡 + 平铺的表"改成"一个状态主卡 + 一条待办 + 一张有时间维度的表"

渲染稿里是 4 处改动，全部只动总览页，**不引入新依赖、不需要新数据**。

### ① 顶部：1 个状态主卡 + 4 个紧凑指标

```
┌──────────────────────────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐
│ 机队状态                      │ │触发中告警│ │agent 落后│ │探测任务 │ │告警规则 │
│ 11 / 12                      │ │   3    │ │  3 台   │ │ 6 / 6  │ │ 4 / 5  │
│ ● 在线 · 1 台离线（DMIT-LAX）  │ │需要处理 │ │最新v0.3.1│ │全部启用 │ │1个已停用│
│ ▓▓▓▓░▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓░    │ └────────┘ └────────┘ └────────┘ └────────┘
│ 30天前   可用率 99.2%   今天   │
│ 需要处理  backup-nas 磁盘 92%  │
│          ucloud-la agent v0.3.0│
└──────────────────────────────┘
```

- **主卡占 2.15fr，另外 4 张各 1fr** —— 用宽度建立层级，不靠加大高度（避免 bento 那种花哨）
- 主卡里三样东西：**当前状态**（在线数 + 哪台离线）、**30 天机队状态条**（聚合各节点的 `uptimeDays`）、**需要处理清单**（从 fleet 派生，两条可点，直接进对应节点面板）
- 30 天条下方标了「30 天前 / 可用率 99.2% / 今天」的轴 —— 这不是装饰：skill 的图表条目明确要求
  **"数值必须始终以文字可见、颜色区间要有文字阈值标注，不能只靠颜色/hover"**

### ② 表格：新增「30 天」列（复用前台已有的状态条组件）

- 每行一条 30 段微条，颜色沿用前台状态页的语义（绿=正常 / 琥珀=抖动 / 灰=无数据）
- 这一列同时解决两件事：**表格终于有时间维度**，以及**把空着的 310px 用掉**
- 前台已经有一模一样的组件（`public/components/uptime-timeline.tsx`），提到 `components/` 共用即可
- 窄屏（< lg）隐藏这一列，不影响 1024 的可读性

### ③ 行高 50 → 44px

12 行时一屏能多放一行，配合"密度高"的定位。分隔线仍只用一种（§BF 才刚把三套机制收敛成两套）。

### ④ 主卡里的「需要处理」清单

把"扫描 12 行找徽章"变成"抬头就看到该处理什么"，两条各是一个链接，直接打开对应节点面板。
数据是**派生**的（关注项超阈值 / agent 落后），不是新字段。

## 三、依据与取舍

- **为什么主卡而不是 6 张等价卡**：等价卡片无法表达优先级。运维台的第一问题是"现在要不要管"，
  所以给"在线/离线"最大权重，其余四张降为紧凑指标。
- **为什么不把说明文字收进 tooltip**：skill 的可视化规范明确禁止"数值只在 hover 可见"。
  渲染稿里 4 张 tile 的说明行**都保留为文字**。
- **为什么用宽度而不是高度做层级**：§BD 刚把卡片从"整卡染色"收敛为"纯白 + 3px 指示条"，
  再用高度差做层级会把节奏重新弄乱。宽度差是克制的一档。
- **为什么加历史列而不是加更多徽章**：徽章是"当下"的重复表达（§BE 的 F6 刚把每行从 7~8 个块砍到 2~4 个），
  再堆徽章会退回原样。时间维度是新信息，不是重复。

## 四、不做的（克制边界）

- 不加渐变、不加玻璃拟态、不加卡片入场动画（§P 已扫过）
- 不引第三方图表库（30 天条是纯 div 分段，前台已有实现）
- 不动侧栏、面包屑、工具栏（§AX/§BF 刚定稿）
- 不改配色体系（仍是 OKLCH + 单一蓝强调色；状态色仍只有绿/琥珀/红三种语义）

## 五、实现路径与工作量

| 改动 | 位置 | 量级 |
| --- | --- | --- |
| 顶部重排（主卡 + 4 tile） | `pages/overview.tsx` KPI 段 | ~130 行改写 |
| 30 天条组件提取 | `public/components/uptime-timeline.tsx` → `components/` | ~30 行搬迁 + 参数化宽度 |
| 表格加「30 天」列 | `pages/overview.tsx` 表格 | ~40 行 |
| 行高与列宽 | 同一文件 | ~5 行 |
| 「需要处理」派生 | 同一文件（纯计算） | ~25 行 |

合计约 230 行改动，**不新增依赖**，前台首屏不受影响（前台已经引了那个组件，只是搬家）。

## 六、风险与验证

| 风险 | 处理 |
| --- | --- |
| 9 列在 1024 变挤 | 30 天列 `hidden lg:table-cell`，并在 1024/1280/1600 三档实测溢出与截断 |
| 主卡变高导致首屏能看的行变少 | 主卡高度与 4 张 tile 对齐（同一行 flex），实测行数不减 |
| `uptimeDays` 从 public mock 提到共用 | 它已经在 `NODES` 里（§BB 统一过），只是组件搬家；提完跑前台快照确认无变化 |
| 状态条颜色对比度 | 逐色测 3:1（图形元素门槛），并入 `check:contrast` |

验证清单（与既有流程一致）：亮/暗 × 5 视口 × 5 页面 溢出/裁剪/孤行/报错 全 0；
对比度闸门全绿；`npm run verify` 24/24；基线重建；前台快照确认未受影响。

## 七、需要你拍板的 4 点

1. **顶部留几个指标？** 现在的 4 张 tile 里，「探测任务」「告警规则」是**配置数量**不是健康指标。
   可以只留 3 张健康指标（告警 / agent / 在线），把这两个配置计数降级成工具栏右侧的纯文本。
   —— 我倾向**保留 4 张**（后台回答"配置齐不齐"也是它的职责），但这条值得你定。
2. **30 天还是 7 天？** 30 天更能体现"长期稳不稳"，7 天更能看出"最近有没有抖"。
   我倾向 30 天（与前台卡片一致）。
3. **行高降到 44 接受吗？** 一屏多看一行，但每行的呼吸感会略减。
4. **主卡的「需要处理」清单会不会与表格的「关注」列重复？**
   我判断不重复：主卡是**行动入口**（可点、只列异常），表格是**全量参考**。如果你觉得重复，可以去掉它，
   只留 30 天条。

定了之后我按这个方案改，并按上面的清单验证。
